# Where the code comes from

The firmware mixes three kinds of code: code the BJT2 team wrote, code that
STM32CubeMX generated from the `.ioc`, and third-party libraries. Every team
source file and every team block inside a generated file now carries a marker
comment. This page explains the markers and lists where everything came from.
Checked on 29 Oct 2026 (commit b8c2351 of the original project repository);
the rows of the 29-30 Oct effect-file work were checked on 30 Oct 2026. The
portrait-screen change added no new files; its one change to third-party code (text Y widened
to 16 bits in the ILI9341 GFX library) is noted in that library's notice.
The serial console and the solo builds (`app_log`, `app_solo`, USART2) were
removed on 1 Nov 2026.

## What the markers mean

| Marker | Meaning |
|---|---|
| `TEAM CODE (owner: Name - subsystem)` at the top of a file | The team wrote this file. Name owns that subsystem. |
| `Authors: ...` under that line | Who actually wrote the lines, when that is not only the owner (usually Brendon as integrator). |
| `TEAM CODE (integration: Brendon)` | Shared glue that Brendon looks after as integrator (RTOS objects, SD fix, build files). `integration: team` means the author is not recorded. |
| `TEAM CODE (owner: Name): what` inside a `USER CODE BEGIN`/`END` block (normally its first line) | That block of a CubeMX file is team code. |
| `TEAM CODE (written by Name, date): what` inside a team file | Another member wrote the lines that follow. |
| `THIRD-PARTY CODE: library` | Not ours and not generated. `Modified by the team:` lists our changes. |
| No marker, ST or CubeMX header | Generated by STM32CubeMX, or copied in by it. |

Search for `TEAM CODE` or `THIRD-PARTY CODE` to find them all.

## The rule for generated files

CubeMX rewrites its files every time someone presses Generate Code. Only the
text between `/* USER CODE BEGIN x */` and `/* USER CODE END x */` survives
(the `.ioc` has `KeepUserCode=true`). So:

- team code in a generated file must stay inside a USER CODE block;
- peripheral settings belong in the `.ioc`, not in hand edits;
- the markers themselves sit inside the blocks, so they survive too.

**Team edits found outside USER CODE blocks: none in the generated C files.**
This comes from the original project repository's git history; CubeMX was
not re-run to prove it. Earlier
hand edits outside the blocks (Jack's May changes to the HAL SD driver,
Brendon's Sep SDIO/DMA edits in `main.c`, the USB VBUS setting, FatFs
`_USE_EXPAND`) were either lost in a regeneration or moved into the `.ioc`. Two build files have no USER CODE blocks at all:

- `cmake/gcc-arm-none-eabi.cmake`: Jack's three `wchar_t` lines for the
  PDM2PCM library (marked). CubeMX writes this file only once, so they
  survive a normal Generate Code. They would only be lost if the file were
  created again from scratch.
- `CMakeLists.txt` (root): CubeMX writes it only once ("User is free to
  modify"). The team sections are marked.

## Open points for the team

- **Owner is not always author.** "Owner" is the subsystem owner from
  `docs/RTOS_ARCHITECTURE.md` section 2. Brendon, as integrator, wrote the
  RTOS port (Sep 2026) and the 28 Oct demo changes inside other members'
  files; the `Authors:` lines say where. The original repository's git
  history alone cannot settle this, because Brendon committed the first import (21 May) and everyone's PD5b
  folders (9 Sep).
- **`sd_detect_override.c`** has no clear owner yet.
- **Inferred origins:** `5x5_font.h` and `fonts.c/.h` have no author or
  licence line. The board settings in the ILI9341 files came with the first
  import; who made them is not recorded.
- **Small contributions noted here only:** Tony's `current_name` field in
  `app_rtos.h` (26 Sep). (Jack's two serial-menu lines in
  `brendon_battery_usb.c`, 30 May, went with the serial menu on 1 Nov 2026.)

The markers are comment-only. A Debug build of the tree before them
(b8c2351 in the original repository) and one of the marked tree, with the same `SOURCE_DATE_EPOCH`, give identical
`arm-none-eabi-size` output and byte-identical `objcopy -O binary` images.
